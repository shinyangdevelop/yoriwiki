# 실제 데이터 기반 검색

## 사용법

홈 검색창, `/search`, `/recipes`에서 동일한 검색 기능을 사용합니다.
검색 상태는 URL에 저장되어 새로고침·뒤로가기·링크 공유 시 유지됩니다.

- 이름·별칭, 재료, 조리 방법, 전체 범위 선택.
- 한글 NFC 정규화, 영문 소문자화, 공백 제거 후 부분 일치.
- 공백으로 나눈 검색어를 모두 포함하는 AND, 하나 이상 포함하는 OR.
- 분류, 최대 조리 시간, 최대 난이도(1~10) 필터.
- 관련도·조리 시간·난이도·좋아요·최신순 정렬. 관련도는 이름 완전 일치 → 접두 일치 → 이름 부분 일치 → 별칭 → 재료 → 본문 순서.
- 한 페이지 12개, 실제 결과 수에 따른 페이지 이동. 필터나 검색어 변경 시 첫 페이지로 이동.
- 검색어 없는 초기 화면은 전체 목록. 명시적으로 빈 검색어를 제출하면 입력 안내와 빈 결과.

`GET /api/search` → Express `/search`가 DB의 레시피를 읽고 메타데이터를 연결한 뒤 정규화 문자열을 비교합니다.
파라미터는 `q`, `field`, `mode`, `category`, `maxTime`, `maxDifficulty`, `sort`, `page`입니다.
SQL 검색 패턴을 조합하지 않으므로 `%`, `_` 등은 와일드카드가 아닌 문자로 검색합니다.
현재 소규모 카탈로그에서는 전체 읽기와 메모리 비교를 사용하며, 데이터가 커지면 정규화 인덱스나 전문 검색으로 확장할 수 있습니다.

## 그래프 데이터 연결 변경

레시피 DB 76개를 확인했습니다. 아래 세 축은 DB에 저장된 값을 직접 사용합니다.

| 축 | 기준 |
| --- | --- |
| 조리 시간 | `estimated_time`의 시간·분 표기를 분으로 변환 |
| 재료 수 | `ingredients`에서 쉼표·줄바꿈으로 구분된 비어 있지 않은 항목 수 |
| 조리 단계 수 | `recipe`에서 1부터 순서대로 매겨진 단계 번호 개수 |
| 난이도 | 이름으로 연결한 `recipe-metadata.json`의 1~10 정수 |

시간·재료 수·단계 수는 76개 모두 표시됩니다. 난이도 메타데이터가 없는 기존 4개는 난이도 축에서 제외하며 값을 임의로 만들지 않습니다.
기존 Convex Hull 표시와 그리디 추천은 같은 API 좌표를 사용합니다.
경험이 없는 계정은 전체 점만 보이며, 실제로 해본 요리를 체크해야 경험 영역이 생깁니다.

## 검증

`npm run test:search`: 제공된 검색 사례, 필터, 정렬, 페이지 이동, 잘못된 입력, 실제 DB 읽기 전용 그래프 좌표 및 추천 검증.
제공된 검색 사례 중 `파마산 치즈`는 기대 결과가 3개로 기록돼 있지만 현재 재료 데이터에는 6개가 일치합니다.
시저샐러드·라자냐·바질페스토파스타를 포함한 6개를 반환하도록 검증했습니다. 생성된 원본 데이터 파일은 변경하지 않았습니다.
