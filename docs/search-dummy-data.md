# 검색용 더미 데이터 전달 명세

이 문서는 다른 에이전트가 생성할 데이터의 계약입니다. 실제 레코드나 seed 파일은 아직 생성하지 않았습니다.
우선 검색 대상은 레시피 제목, 재료, 조리 방법입니다. 재료 사전·커뮤니티 검색은 현재 backend 모델이 없어 별도 범위입니다.

## 1. 현재 API와 바로 호환되는 필수 데이터

UTF-8 JSON 파일 `backend/data/recipes.json`에 객체 배열을 생성합니다.
각 객체는 아래 네 필드를 모두 가지며 값은 빈 문자열이 아닌 **문자열**이어야 합니다.

| 필드 | 형식 및 내용 |
| --- | --- |
| `name` | 고유한 한글 요리 이름. 앞뒤 공백 제거, NFC 정규화 |
| `ingredients` | 재료명·수량·단위를 포함한 일반 텍스트. 재료 하나당 줄바꿈 `\n` 하나. JSON 배열이나 중첩 객체로 저장하지 않음 |
| `recipe` | 순서 번호가 있는 조리 설명. 단계별 줄바꿈 `\n`. 검색 가능한 자연어 문장 |
| `estimated_time` | 양의 정수 분 단위에 `분`을 붙인 문자열. 모든 레코드에서 같은 형식 사용 |

현재 `POST /api/food`에 객체 하나씩 전달할 수 있습니다. 응답은 생성된 숫자 ID입니다.
`id`는 SQLite 자동 생성값이므로 입력 파일에 지정하지 말고, import 시 응답 ID를 기록하세요.
`name`은 UNIQUE이므로 재실행 시 중복 이름을 처리하는 import 정책이 필요합니다.
기존 `backend/database.db`는 삭제하거나 덮어쓰지 마세요.
현재 목록 응답은 `id`, `name`, `estimated_time`만 포함하고 상세 조회는 네 필드를 모두 포함합니다.
재료·본문 검색은 향후 backend 검색 쿼리에서 구현해야 하며 목록 응답만으로 검색하면 안 됩니다.

## 2. 화면의 필터·정렬까지 구현할 때 필요한 확장 데이터

아래는 **현재 API가 저장하지 않는 필드**입니다. 필수 입력과 분리한
`backend/data/recipe-metadata.json` 배열로 준비하고 `name`으로 연결합니다.
실제 검색 구현 시 DB 마이그레이션과 API 확장을 먼저 수행해야 합니다.

| 필드 | 형식 및 내용 |
| --- | --- |
| `name` | 필수 데이터와 정확히 일치하는 고유 이름 |
| `description` | 카드에 표시할 요약 문자열 |
| `category` | `한식`, `중식`, `일식`, `양식`, `베이킹`, `간식` 중 하나 |
| `difficulty` | `쉬움`, `보통`, `어려움` 중 하나 |
| `cooking_time_minutes` | 양의 정수. `estimated_time`과 동일한 분 수 |
| `servings` | 양의 정수 인분 |
| `tags` | 중복 없는 문자열 배열. 식사 상황·요리 특성 등 |
| `ingredient_names` | 수량을 제외한 정규화된 재료명 배열. 필수 데이터의 재료와 일치 |
| `step_count` | 양의 정수. 번호가 매겨진 조리 단계 수. 경험 지도에 필요 |
| `aliases` | 띄어쓰기 변형·대체 명칭 문자열 배열 |
| `likes` | 0 이상의 정수. 평점과 구분 |
| `created_at` | UTC ISO 8601 문자열. 최신순 정렬용 |
| `image_url` | 선택 필드, 사용 가능한 이미지 URL 또는 null |

평점 검증이 필요하면 별도 파일에 `name`, `rating`(1~5 정수), `comment`(문자열 또는 null)를 준비합니다.
현재 `POST /api/food/rate?name=...`로 입력하며 평균·평가 수는 서버에서 계산합니다.

## 3. 데이터 분포와 검색 검증 정보

- 권장 60~100개. 각 분류·난이도를 포함하고 동일 재료를 공유하는 여러 레시피를 포함합니다.
- 조리 시간 15분·30분·60분의 바로 전/정확한 값/바로 다음 값을 포함해 경계 필터를 검증합니다.
- 제목에만 검색어가 있는 경우, 재료에만 있는 경우, 본문에만 있는 경우를 각각 포함합니다.
- 비슷한 요리명, 띄어쓰기 변형, 한글·영문 재료명, 여러 재료 조합, 긴 본문을 포함합니다.
- 좋아요 0, 동률, 작성일 동률을 포함해 정렬 안정성을 검증합니다.
- `search-cases.json`에 `query`(문자열), `fields`(검색 필드 배열), `expected_names`(기대 이름 배열),
  `match_rule`(부분 일치/재료 AND 등 설명)을 기록합니다. 결과 없음과 공백 입력도 포함합니다.
- 검색의 별칭 처리·공백 정규화·다중 재료 AND/OR 정책은 아직 구현되지 않았으므로 검증 사례에 기대 정책을 명시합니다.

생성 후 JSON 파싱, 필수 필드 타입, 이름 중복, 메타데이터 연결 누락,
시간 필드 일치 및 enum 범위를 검증하고 검증 결과를 함께 전달하세요.

## 탐색 기능 연결 안내

탐색 페이지는 `recipe-metadata.json`을 읽도록 구현되었습니다. `name`, `cooking_time_minutes`,
`ingredient_names`, `step_count`, `difficulty`를 모든 요리에 제공하세요.
레시피 본문에서 값을 추정하지 않으므로 이 값들이 있어야 지도·추천을 온전히 사용할 수 있습니다.
기존 API가 확장 필드를 DB에 저장하지 않는 점은 동일하며, 탐색 API가 파일을 읽어 연결합니다.
자세한 계산 규칙은 [탐색 알고리즘](exploration-algorithms.md)을 참고하세요.
